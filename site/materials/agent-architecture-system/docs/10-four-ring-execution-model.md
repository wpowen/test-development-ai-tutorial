# 10 四环执行模型：取代线性瀑布门禁

## 10.0 给完全没接触过的人

传统流程是一条直线：写代码 → 跑测试 → 通过 → 上线 → 结束。

Agent 不能这样，因为它上线后**行为会变**（模型静默更新、数据漂移、攻击面变化）。所以测试不是一条直线，是**四个不断转的环**，每个环用不同的输入、不同的速度、回答不同的问题。

## 10.1 四个环

| 环 | 触发 | 时长 | 覆盖维度 | 门禁性质 |
| --- | --- | --- | --- | --- |
| **环 1 离线 CI** | 每次提交 | ≤ `<10 min>` | D1 核心子集、D4-3、D5 静态规则 | **硬门禁**，失败阻断合并 |
| **环 2 沙箱回放** | 每日 / PR 合并 | ≤ `<2 h>` | D1 全量、D2、D4 全量、D5 全量 | **硬门禁**，`pass^k` 不达标阻断发布 |
| **环 3 影子 + 灰度** | 每次发布 | `<shadow_window>`，由风险 owner 配置 | D3、D6、D7-1（真实流量不生效） | 软门禁，看在线指标 |
| **环 4 在线持续评估** | 持续 | 持续 | 按 `<sampling_policy>`；高危动作按 `<capture_policy>` | 告警 + 场景化回滚 |

## 10.2 为什么必须有环 4

| 观测 | 数值 |
| --- | --- |
| 来源中的停止监控个案 | 在其观察窗口内出现质量退化；不可外推为通用期限或必然规律 |
| 持续评估相比周期性评估可降低的生产事故 | 约 **67%** |

**关键做法**：生产监控应使用**与开发阶段相同的评估器**给线上流量打分。这样才能当天发现回归，而不是几周后从工单里发现。

这一条与 D0 直接相连：线上用小模型 judge 采样，必须被前沿 judge + 人工标注校准，否则线上分数只是便宜的噪声。

## 10.3 环 3 影子模式的做法

真实用户请求**同时**打给旧版和新版：

```text
用户请求
   ├──► 旧版 ──► 结果返回给用户，动作照常执行
   └──► 新版 ──► 结果【不返回给用户】【不执行任何动作】
                 只落 trace 并打分
```

**零风险拿到真实分布上的对比数据。** 这是交易类 Agent 最重要的一道保险。

### 影子模式的三个纪律

```text
□ 新版必须真的「不生效」——测试要验证它确实没有产生副作用
□ 输出不一致 ≠ 错误。必须先用 Oracle 判定差异性质，再决定是否阻断
   （否则每次模型升级都会因措辞变化被全部拦下）
□ 影子期长度要覆盖业务周期（含周末、月末结算等特殊分布）
```

## 10.4 环间不能互相冒充

这是本模型最重要的纪律。

| 环 | 能证明什么 | **不能**证明什么 |
| --- | --- | --- |
| 环 1 | 确定性规则与静态契约成立 | 模型行为可靠 |
| 环 2 | 在**固定回放集**上分布达标 | 在真实流量分布上达标 |
| 环 3 | 在真实流量上分布可比 | 生效后的业务结果 |
| 环 4 | 生产上正在发生什么 | 未来不会漂移 |

**跨环升级必须有新的输入、新的 owner 和回滚证据。** 把环 2 的绿色写成"生产可用"是成熟度冒充（违反 [公理 6](https://local/methodology/01-公理与责任模型.md)）。

## 10.5 每个环必须声明的五件事

```text
population    这个环跑的是什么总体（回放集？真实流量？采样比例？）
统计方法      点估计还是区间？聚类单位是什么？
owner         这个环的结果由谁负责解读
hard block    哪些条件会硬阻断
rollback      失败时回滚什么（模型/prompt/工具/记忆 四维成组）
```

缺任何一项，这个环的结果都不能作为发布证据。

## 10.6 与 CI 分层门禁的映射

方法论主手册的 Gate-1..4（[05 章 7.4 节](https://local/methodology/05-阶段方法-设计到执行.md)）与四环的对应：

| 主手册 | 本维度 | 差异 |
| --- | --- | --- |
| Gate-1 每次提交 | 环 1 离线 CI | 一致 |
| Gate-2 MR 合并前 | 环 2 沙箱回放（部分） | Agent 增加了轨迹回放与 `pass^k` |
| Gate-3 每日/RC | 环 2 全量 | Agent 增加攻击集与统计门禁 |
| Gate-4 发布前 | 环 3 影子灰度 | **Agent 新增**：传统系统很少做影子 |
| —— | **环 4 在线持续** | **Agent 独有**：传统系统上线后行为稳定 |

**环 4 是 Agent 相对传统系统最本质的新增。**

## 10.7 可运行练习

```bash
cd materials/agent-architecture-system
python3 scripts/agent_reliability_lab.py rings --input fixtures/four-ring-plan.json
python3 scripts/agent_reliability_lab.py rings --input fixtures/four-ring-plan.json --fault fake-online-pass
```

基线：环 1/2 生成 receipt，环 3/4 明确标记 `NOT_RUN`，退出 `0`。
故障：把环 4 伪造成 `PASS` 后退出 `1`，指名 `RING/MATURITY-CLAIM`——因为本地夹具不可能产生在线证据。

## 10.8 证据边界

来源中的固定时间窗口与事故降幅是**特定样本观察**；本课程只保留“需要持续监控和回灌”的教学功能，不把数值当行业阈值。
环 3、环 4 在本项目中**从未运行**（`NOT_RUN`）：没有真实流量、没有生产接入、没有在线采样。
本维度只提供环 3/4 的**设计与接口形状**，任何"影子通过"或"在线达标"的表述都属于越界声称。
