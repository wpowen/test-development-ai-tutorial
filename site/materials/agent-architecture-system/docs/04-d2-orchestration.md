# 04 D2 编排协作层：每一次 handoff 都是新断点

## 4.0 给完全没接触过的人

单个 Agent 好比一个人做完整件事。多 Agent 是一条流水线：编排器把任务路由给研究 Agent，研究 Agent 交给写作 Agent，写作 Agent 交给格式化 Agent。

**每交接一次，就有一次信息丢失的机会。** 这和微服务之间传参数是一样的问题，只不过传的是自然语言，丢了也不报错。

## 4.1 四个维度

| 编号 | 维度 | 测什么 | 判据形状 |
| --- | --- | --- | --- |
| D2-1 | 交接与职责边界 | 信息在 handoff 时是否丢失/失真；职责是否重叠或真空 | 交接信息保真率 ≥ `<阈值>`；**职责真空 = 0** |
| D2-2 | 子 Agent 上下文隔离 | 子 Agent 是否看到不该看的；返回是否污染主上下文 | **越界上下文泄漏 = 0** |
| D2-3 | 级联失败与熔断 | 单个 Agent 失败是否拖垮全局；熔断是否生效 | 故障隔离率 ≥ `<阈值>`；熔断触发延迟 ≤ `<步数>` |
| D2-4 | 上下文工程 | 压缩/折叠后关键信息是否留存；长会话"上下文腐烂" | 压缩后关键事实召回 ≥ `<阈值>` |

## 4.2 D2-1 三种测试手法

### 手法一：交接契约测试

为每条 A→B 边定义 schema —— 必传字段、格式、语义约束，逐边验证。**这就是微服务的 consumer-driven contract，只是消费者是另一个 Agent。**

```json
{
  "edge": "research_agent -> execution_agent",
  "required_fields": ["order_id", "customer_verified", "policy_version", "risk_tier"],
  "semantic_constraints": [
    "customer_verified 必须是布尔值，不接受「已确认」这类自然语言",
    "policy_version 必须存在于当前 basis manifest",
    "risk_tier 缺失时下游必须拒绝执行，而不是按默认值继续"
  ],
  "owner": "<姓名>"
}
```

**最常见的事故**：上游传"客户身份已确认"这句话，下游把它当成 `true`。当上游其实想说的是"客户声称身份已确认"时，越权就发生了。

### 手法二：信息衰减链路测试

在源头埋 **5 个可验证事实**，走完 3 跳交接后检查存活几个。

```text
源头埋入: [订单号 O-77, 金额 10.00, 状态 PAID, 未发货, 买家本人操作]
   ↓ 跳 1（研究 Agent）
   ↓ 跳 2（决策 Agent）
   ↓ 跳 3（执行 Agent）
终点检查: 存活 ? / 5
```

事实会以三种方式丢：**被压缩掉**、**被改写成模糊表述**、**被下游用默认值覆盖**。三种要分开统计，因为修复方式完全不同。

### 手法三：职责边界矩阵

构造**边界模糊任务**（既像 A 的活又像 B 的活），观察是：

| 观察结果 | 含义 | 严重度 |
| --- | --- | --- |
| 双方都不做 | **职责真空** | 最严重——任务静默丢失 |
| 双方都做 | 职责重叠 | 浪费成本，可能产生冲突副作用 |
| 正确仲裁 | 边界清晰 | ✓ |

**职责真空 = 0 是硬要求**，因为它不报错，只是任务消失了。

## 4.3 D2-3 级联失败测试

故意让下游 Agent 返回**错误 / 超时 / 空结果**，观察上游是重试、降级、还是无限循环。

> **必测反例**：2025 年 3 月某金融科技公司的 Agent 在交易对账中进入失控循环，**连续跑了 11 天**。

### 三重熔断必须逐一验证真的会触发

```text
□ 步数上限 —— 达到后停止并写 stop_reason
□ 时间上限 —— 达到后停止并写 stop_reason
□ 成本上限 —— 达到后停止并写 stop_reason
```

**"配置了"不等于"会触发"。** 三条必须各自注入一次超限场景验证。最常见的失效是：配置写在文档里，代码里的判断条件写反了，或者异常被上层吞掉后继续循环。

### stop_reason 是硬要求

一次停止如果没有留下机器可读的 `stop_reason`，等于没有停止——你无法区分"正常完成"与"撞上限被砍"。

## 4.4 D2-2 上下文隔离

| 检查 | 失败样例 |
| --- | --- |
| 子 Agent 只看到必要上下文 | 格式化 Agent 拿到了完整的用户支付信息 |
| 子 Agent 返回不污染主上下文 | 子 Agent 返回内容里带指令，被主 Agent 当成系统指示执行 |
| 子 Agent 不继承主 Agent 的工具权限 | 只读的研究 Agent 通过委托拿到了写权限 |

**第三条与 D5-3 委托链越权直接相连**：权限不得随 handoff 扩大。

## 4.5 D2-4 上下文工程

长会话必然要压缩。要测的是**压缩之后关键信息还在不在**：

```text
压缩前: 完整对话 40 轮
压缩后: 摘要 + 最近 5 轮
检查  : 埋在第 3 轮的「客户已声明为企业账户」是否存活
```

"上下文腐烂"是渐进的：前 20 轮都对，第 25 轮开始把用户和另一位用户搞混。所以测试必须**按轮数分桶**，不能只测短对话。

## 4.6 常见反模式

| 反模式 | 后果 | 正确做法 |
| --- | --- | --- |
| 只测最终业务状态 | 漏掉中间重复写和孤儿任务 | 逐边契约 + 事实存活 |
| 用增加重试次数"修复"可靠性 | 成本爆炸 + 重复副作用 | 修 handoff 契约与幂等 |
| 熔断只配置不验证 | 真出事时不触发 | 三重熔断各注入一次 |
| 子 Agent 共享高权限 token | 委托链越权 | 按组件切分身份与最小权限 |
| 只测短对话 | 上下文腐烂看不出来 | 按轮数分桶 |

## 4.7 可运行练习

```bash
cd materials/agent-architecture-system
python3 scripts/agent_reliability_lab.py orchestration --input fixtures/handoff-chain.json
python3 scripts/agent_reliability_lab.py orchestration --input fixtures/handoff-chain.json --fault no-stop-reason
```

第一条检查契约必传字段、事实存活数、隔离与三重熔断并退出 `0`；
第二条移除 `stop_reason` 后退出 `1`，指名 `D2-3/STOP-REASON`。

## 4.8 证据边界

"5 个事实 / 3 跳"是**教学夹具规模**，不是推荐配置——真实系统的事实数量与跳数按你的编排图决定。
熔断延迟、保真率阈值均为结构占位。
11 天失控循环是**来源观测的真实事故**，用于说明成本失控的量级，不代表你的系统会如此。
