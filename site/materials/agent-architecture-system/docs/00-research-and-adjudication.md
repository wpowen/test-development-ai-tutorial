# 00 调研与裁决：为什么 Agent 需要一套单独的测试架构

> 学习者投影副本，正文同源于仓库 methodology/dimensions/agent-testing-architecture/。
> 本维度对应课程模块 **TD-M12**（11 页：TD-AG-00 … TD-AG-10）。
> 上游来源：`research/user-input/AI-agent测试架构.txt`（v2.0，2 sources / 198 sections / 413 atoms 已冻结吸收）+ `research/topics/TD-AG-*/` 逐题九件研究包。

## 0.1 一句话结论

**传统测试体系的骨架（分层、门禁、回归）在 Agent 上仍然成立，但有五处结构性假设已经失效。**
不是"再加几个用例"能补的，必须换掉四件东西：判定单位（点 → 分布）、评测对象（终局 → 轨迹）、评估器地位（可信基础设施 → 被测系统）、安全时机（发布前一次 → 贯穿运行时）。

## 0.2 五个失效点（逐条给出证据与推论）

### 失效点 1：瀑布式布尔门禁套在非确定性系统上

传统门禁每层是"通过 / 失败"的一次性判定。**同一输入返回不同结果，在传统软件里是 bug，在 LLM 驱动的 Agent 里是正常行为。**

| 观测 | 数值 | 来源类型 |
| --- | --- | --- |
| τ-bench 零售 Agent：`pass@1` | 61% | 公开基准 |
| 同一 Agent：`pass^8`（8 次全对） | 25% | 同上 |
| Claw-Eval：错误注入下 `Pass@3` | 相对稳定 | 公开基准 |
| 同上：`Pass^3` | **下跌多达 24 个百分点** | 同上 |

**推论**：单次通过率**完全掩盖**了一致性崩塌。一个报"通过率 95%"的 Agent，可能在"每次都对"的口径下只有 30%。你对用户承诺的是后者。

> ⚠ 上表数值是**公开基准上的观测**，不是你的系统的预期值，也不是阈值建议。它证明的是"两个口径可以差得极远"这件事本身。

### 失效点 2：只评最终输出，不评轨迹

| 观测 | 数值 |
| --- | --- |
| 只对最终输出打分会漏掉的失败模式 | 约 **90% 发生在执行中途** |
| 轨迹不透明的评估漏掉的安全违规 | **44%** |
| 轨迹不透明的评估漏掉的鲁棒性失败 | **13%** |

**推论**：终局正确不能抵消中途越权。"Agent 最终回复转人工"听起来完美，但它此前已经调过一次退款接口——只是被后端拒了。

### 失效点 3：把评估器当成可信基础设施（最大盲区）

整个体系依赖 judge 打分，却**从不测 judge 本身**。

| 观测 | 数值 |
| --- | --- |
| prompt 措辞、judge 选择、温度等流水线因素带来的方差，比朴素置信区间高出 | **40–60%** |
| judge 分歧在安全分类任务中贡献的总方差占比 | 高达 **44%** |
| 实测案例：供应商在同一模型名下静默更新导致 κ 漂移 | 0.72 → **0.58**（团队毫无察觉） |

还有一个更隐蔽的问题——**元评估漂移（Meta-Evaluation Drift）**：递归式 LLM 评估会变得内部自洽，却与人类判断和任务真实目标逐渐脱节。分数越来越稳定、越来越好看，与现实的距离越来越远。

**推论**：**judge 的 κ 就是你所有评估数字准确性的上限。** 这件事在多数团队里从未被量化过。

### 失效点 4：安全测试作为发布前的一次性门禁

攻击面已经从"用户输入"转移到"**运行时数据通道**"。

MCP 工具投毒的根因是**连接时与运行时的信任落差**：工具描述只在首次连接时审一次，工具响应却直接进上下文、毫无等价检查。

| 观测 | 数值 |
| --- | --- |
| MCPTox 基准（45 个真实 MCP server / 353 个真实工具）：多数流行 Agent 攻击成功率 | 超过 **60%**，最高 **72%** |
| 反直觉发现 | **能力更强的模型往往表现更差**——更强的指令遵循让它们对恶意元数据更顺从 |
| 2026 年披露的存在风险的 MCP 实例 | 多达 **20 万个** |

**推论**：安全不能是发布前的一道门禁，必须贯穿四个环持续对抗。而且"换更强的模型"不是安全修复。

### 失效点 5：上线前测试为主，缺少在线持续评估

| 观测 | 数值 |
| --- | --- |
| 上线前测充分、上线后停止监控的团队 | **30–60 天内质量必然退化** |
| 持续评估相比周期性评估可降低的生产事故 | 约 **67%** |
| 已在生产运行 Agent 的组织 | 57% |
| 其中会在部署前做离线评估的 | 仅 **52%** |

**推论**：发布不是终点。Agent 会漂移，而漂移只有持续评估能发现。

### 三个附加缺口

| 缺口 | 说明 |
| --- | --- |
| 多 Agent 编排完全未覆盖 | 企业部署越来越跑在多 Agent 架构上，**每一次 handoff 都是新断点** |
| 成本不是一等指标 | 某金融科技 Agent 在交易对账中进入失控循环，**连续跑了 11 天** |
| 无 Agent 身份与委托链治理 | 企业机器身份与人类身份比已达 **82 : 1** |

## 0.3 裁决：v1.0 → v2.0 的结构变更

| 变更类型 | 内容 |
| --- | --- |
| **新增域** | D0 评估可信层（4 维）、D2 编排协作层（4 维） |
| **范式重构** | D4 从"布尔通过"改为"**可靠性分布**" |
| **大幅扩展** | D5 安全从 2 维扩到 **6 维**，且前移为持续测试 |
| **新增机制** | 四环执行模型、运行时护栏、三段式门禁 |
| **合并降级** | "兼容性测试"并入 D6；"边界条件"并入 D4 |
| **规模** | 7 层 23 维 → **8 域 36 维** |

## 0.4 为什么这四件事必须一起换

它们不是四个独立改进，而是一条依赖链：

```text
D0 judge 可信  ──决定──►  所有分数的准确性上限
      │
      └── 分数可信后，D4 的分布判定才有意义
                │
                └── 分布判定需要 D1 的 span 轨迹来定位「在哪一步坏的」
                          │
                          └── 定位之后，D5 的持续对抗才知道该守哪一层
```

**如果只能做一件事：先做 D0-1（judge 校准）。** 你现在所有评估数字的准确性上限都取决于那个 judge 有多准——而这件事大概率还没有被量化过。

## 0.5 证据分级

按 [方法论 01 章 1.5](https://local/methodology/01-公理与责任模型.md) 的三类断言分离：

### Evidence（来源直接支持）

- 公开基准（τ-bench、Claw-Eval、MCPTox、HORIZON、METR、ATBench、Agent-SafetyBench、ToolEmu）上的 `pass@k` / `pass^k` 差距、轨迹遮蔽导致的漏检率、MCP 攻击成功率。
- OWASP Top 10 for Agentic Applications（ASI01–ASI10）对攻击类别的划分。
- NIST AI RMF、ISO/IEC 42001、EU AI Act Art.14（人类监督）/ Art.15（网络安全）对人类监督与安全的要求。
- judge 方差分解研究对流水线因素方差占比的测量。

### Inference（跨来源综合的工程设计）

- **8 域 36 维的划分方式**、域间依赖顺序、四环执行模型、三段式门禁——这是把上述证据编码成可执行架构的工程综合，不是任何单一标准要求的固定结构。
- "先做 D0"的优先级排序。
- 爆炸半径三维标签（可逆性 × 影响面 × 资金影响）。
- 高风险适配器中"建议 / 执行"物理隔离的做法。

### Unknown（当前证据无法回答）

```text
UNKNOWN  你的 Agent 在你的任务集上的 pass^k 分布
UNKNOWN  你的 judge 与你的领域专家的 κ
UNKNOWN  你的工具清单在 rug-pull 下的实际拒绝率
UNKNOWN  你的成本 P99 与失控循环的实际触发条件
UNKNOWN  本架构在任何真实组织落地后的事故率变化
```

**这五项必须由你自己实测。本维度提供的是测量方法与判据结构，不是这些数值。**

## 0.6 数值的使用纪律

本维度文档中出现的**所有百分比、κ 值、k 值、时长、金额**分两类：

| 类别 | 例子 | 怎么用 |
| --- | --- | --- |
| **来源观测**（有出处） | τ-bench pass^8 = 25%；MCPTox ASR > 60% | 用来论证"这个问题真实存在"，**不得**当作你系统的预期值 |
| **结构占位**（无出处） | κ ≥ 0.7；pass^5 ≥ 80%；P0 任务 k=10 | 用来说明**判据的形状**，阈值必须按 [08 度量体系 8.6 节](https://local/methodology/08-度量体系.md) 实测后重设 |

⚠ 直接把 `κ ≥ 0.7` 抄进你的门禁，会得到一个既不阻断真问题、又天天误报的检查。
