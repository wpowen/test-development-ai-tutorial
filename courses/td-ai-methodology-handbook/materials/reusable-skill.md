# 可复用 Skill：把方法论门禁接到你自己的工件上

这份 Skill 描述如何把本课程的七道门禁迁移到你的项目，而不是复制订单取消的业务规则。

## Skill 边界（写进 System 段）

```text
角色：质量流程门禁助手。你检查工件结构、追溯闭包与状态传播，不裁决业务规则。
规则：
1. 每条判断必须指名具体工件与字段；不得输出笼统的「校验不通过」。
2. 来源冲突输出 BLOCKED 并要求升级责任人；不得选择更合理的一方。
3. 文档未定义的内容输出 UNKNOWN；不得补写。
4. 不得批准 Waiver、不得作出发布决定、不得修改业务期望值。
5. 阈值一律视为占位；缺 owner 的阈值输出 UNKNOWN 而非默认值。
6. 不处理生产密钥、真实支付账号或未脱敏个人信息。
```

## 迁移步骤

1. **保留不变的部分**：七道门禁的语义、状态词（`BLOCKED` / `UNKNOWN` / `UNSUPPORTED_RULE` / `SUPERSEDED`）、fail-closed 原则、Waiver 四条禁令、语义层不得单独放行 blocker。
2. **必须替换的部分**：业务对象与来源优先级规则、风险打分口径与分档边界、Oracle 独立来源、blocker 切片定义、Waiver 批准角色。
3. **先做窄链**：只选一个高风险需求跑完 S1→S9，不要一次铺开全部需求。
4. **验证迁移成功的标准**：不是「命令跑通了」，而是「一个已知缺陷能在你的门禁上稳定变红，且失败信息足以定位到层」。

## 接入方式

### 方式 A：直接复用夹具结构

把 `examples/` 六份 JSON 换成你的工件，`schemas/` 五份 Schema 按你的字段扩展，其余不动。适合先验证流程是否合用。

### 方式 B：只借门禁语义

保留 `scripts/validate_handbook.py` 中 `gate_basis` / `gate_requirement` / `gate_risk` / `gate_oracle` / `gate_run_receipts` / `gate_release` / `gate_closure` 七个函数的判断逻辑，用你自己的数据源实现。适合已有工件管理系统的团队。

### 方式 C：接进 CI

把 baseline 命令放进 Gate-2，把五类故障注入放进 Gate-3 的自检（验证门禁本身没有退化）。门禁执行失败等同于不通过，不得视为跳过。

## 反模式

```text
✗ 把阈值直接抄过去（本包所有数值都是结构占位）
✗ 让同一个模型既生成工件又判定工件
✗ 用「团队一直这么做」替代方法选择理由
✗ 把 UNKNOWN 桶清空以求报表好看
✗ 给 Waiver 写「长期有效」
```

## AI 能做与不能做

模型可以：抽取候选字段、解释门禁失败信息、起草模板初稿、对失败做聚类候选。

模型不能：裁决业务规则冲突、批准自己的输出、签发 Waiver、作出发布决定、把 `UNKNOWN` 补写成一个听起来合理的根因。这些边界由 `judge-self-approval` 与 `expired-waiver` 两类故障在夹具中强制。
