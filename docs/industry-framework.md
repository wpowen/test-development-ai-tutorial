# 测试开发 × AI：职业知识系统

状态：`desk-researched`。本框架基于测试职业体系、标准、官方技术文档、开源实现、公开岗位和从业案例重建；它用于检查课程是否全面，不等于企业生产验证或学员学习效果证明。

## End-to-end lifecycle

测试开发的主线不是“写用例 → 跑用例”，而是把业务风险连续转化为可审计证据：

`质量目标 → 需求与规则 → 风险与策略 → 静态预防 → 测试分析/设计 → 数据/环境/自动化 → 执行 → 结果与缺陷 → 发布决策 → 生产观测 → 复盘改进`

每一步都必须回答六个问题：输入是什么，谁负责，产生什么工件，用什么指标判断，失败会影响谁，结论交给谁。ISTQB CTFL v4.0.1 将测试活动拆为计划、监控与控制、分析、设计、实现、执行和完成；ISO/IEC/IEEE 29119-2 给出测试过程框架。课程在此基础上补上测试开发常见的工程实现、持续交付、生产反馈和 AI 系统质量责任。

完整链路的核心工件包括：质量目标与风险登记册、需求评审记录、双向追踪矩阵、测试策略、测试条件与用例、数据卡、环境清单、自动化仓库、执行证据、缺陷与根因、发布报告、SLI/SLO、事故与回归资产。任何“AI 提效”都必须明确改动其中哪一个工件、保留哪一个人工责任，以及如何证明没有丢失质量信息。

## Specialization families

课程不能只覆盖功能和 UI 自动化。测试行业至少要形成以下专项族：

1. 需求、业务规则、验收与探索性测试；
2. 单元、组件、API、契约、集成、消息和端到端测试；
3. UI、兼容性、国际化、可访问性和真实用户旅程；
4. 测试数据、数据库、数据管道、血缘、脱敏与数据质量；
5. 性能、负载、压力、峰值、突发、容量、长稳、扩展性与成本；
6. 可靠性、可用性、恢复、灾备、降级、混沌和错误预算；
7. 安全、认证授权、API abuse、依赖供应链、隐私与密钥；
8. 可观测性、日志、指标、Trace、告警、合成监控和 Runbook；
9. 自动化架构、测试平台、CI/CD、证据归档与维护成本；
10. LLM、RAG、多模态、Agent、Workflow、Benchmark 和 AI 治理。

每个专项都必须有受保护的质量结果、风险、方法、可重放工件、指标、工具、故障注入和退出门槛。例如 API 测试不能停在 200 状态码；还要覆盖 HTTP 语义、Schema、业务规则、认证授权、幂等、分页、限流、错误模型、版本和消费者契约。性能测试不能停在压测脚本；还要有工作负载模型、p50/p95/p99、错误率、吞吐、饱和、容量拐点、长稳和成本。

## System and work-object classes

测试人员面对的对象已经从“页面和接口”扩展为一组相互依赖的系统：需求文档和规则、代码和配置、UI 与客户端、HTTP/gRPC/API、微服务与事件、数据库和数据管道、CI/CD 与生产基础设施、基础模型与推理端点、Embedding/RAG、工具调用、Agent/Worker/Workflow，以及 Trace/Eval/Benchmark 数据。

不同对象需要不同证据。文档需要可测试性与追踪；API 需要合同与状态；分布式系统需要超时、重试、一致性和恢复；LLM 需要版本化输入、重复运行、风险切片和组合 Oracle；Agent 还要检查工具、参数、权限、轨迹、状态、终止和副作用。课程如果只给一个通用 Prompt 而不声明操作对象，就不能算职业能力。

## Quality and outcome attributes

专业课程按质量属性决定方法，而不是按工具品牌决定方法。主属性包括正确性与完整性、性能效率、兼容与互操作、交互与可访问性、可靠性与可恢复性、安全与隐私、可维护与可测试性、成本与资源效率，以及 AI 特有的事实性、拒答、鲁棒性、偏差、工具安全和可追溯性。

每个属性必须同时有：可观察指标、领先指标、滞后指标、工作负载或风险切片、分布而非只有平均值、阈值、决策责任人和权衡说明。AI 性能至少区分 TTFT、TPOT/ITL、端到端延迟、请求吞吐、输出 Token 吞吐、Goodput、队列、运行/等待请求、GPU/KV Cache、错误率、重试放大和单位成功任务成本。不存在脱离业务工作负载的通用“合格数值”。

## AI transformation

AI 对职业的变化分成六类，而不是简单写“替代测试”：

- `retained`：风险判断、Oracle、探索、发布责任、高风险安全/合规决策仍由人负责；
- `assisted`：AI 可解析需求、枚举风险、生成候选测试、聚类日志，但结论必须引用证据并由人验证；
- `automated`：Schema 校验、静态分析、执行编排、证据归档等有明确输入输出和回退的步骤可自动化；
- `transformed`：测试数据变成带版本与风险切片的 Eval 数据，固定断言变成确定性规则、语义 Judge 和人工审核的组合 Oracle；
- `new-work`：模型/Prompt/知识库/工具/Scorer 版本，非确定性、污染、漂移、提示词注入、越权、Agent 副作用、TTFT/TPOT 和 AI 成本成为新责任；
- `declining`：机械抄写 CRUD 用例、重复执行和模板化汇报的比重可能下降，但公开证据不足以推导“测试岗位消失”。

Google 2026 年的 SRE AI 实践仍强调 Agent 的身份和权限、可靠性 SLO、回退、透明轨迹、持续评测和生产状态控制。这支持“从执行自动化升级为受控质量系统”，而不是无监督替代。

## Role and career evolution

职业路径由“执行多少用例”转向“能否拥有风险到证据的闭环”。初级人员需要会拆需求、设计 Oracle、维护数据环境和读懂失败；测试开发需要编程、API/集成、CI、可观测性和测试平台；资深质量工程师需要性能、可靠性、安全、发布与生产反馈；AI Quality Engineer 还需要 Eval 数据、Scorer/Judge 校准、LLM/RAG/Agent/Workflow 评测、Benchmark、成本和治理；平台/负责人需要定义质量系统、Waiver、SLO、事故和能力演进。

“开发和测试融合”不意味着测试思想消失。ISTQB 的 whole-team approach 表示质量由全团队共同负责；测试专业人员的差异化价值转向风险、可测试性、系统性反例、复杂诊断、平台门禁和独立证据。DORA 报告、AI Quality 岗位和 Google SRE 案例属于方向信号，不能单独证明所有公司都会采用同一岗位名称。

## Coverage verdict

本次架构已把课程扩为五条相互依赖的路线：传统全生命周期、测试专项、大模型与 AI 系统基础、AI 应用于测试、AI 系统与质量平台。新增课程明确覆盖需求解析、追踪、分层策略、数据环境、API 契约、UI/兼容/可访问性、性能容量、可靠性安全可观测性、AI 接口、AI 性能、容量诊断、稳定性、Serving 可观测性和职业演进。

当前可确认的是“知识架构和研究覆盖已经补齐到专业框架级别”。不能确认的是所有课程都已完成实验、真实供应商压测、企业生产有效、资深从业者盲审或初学者学习增益。站点必须按页面显示 `资料已审 / 实验已跑 / 待开发`，不能用完整目录冒充完整交付。

## Critical gaps

以下缺口已分配到明确课程和验收门槛，因此不再是无主缺口：真实 AI API 适配与费用预算进入 TD-AI-21；TTFT/TPOT/Goodput 进入 TD-AI-22；容量与瓶颈进入 TD-AI-23；限流、重试、Fallback 与副作用进入 TD-AI-24；Queue/GPU/KV Cache/Trace 进入 TD-AI-25；角色转型与作品集进入 TD-AI-26。

仍未完成的验证边界：除现有 RAG fixture 外，新增专题尚未建立全部可运行实验；没有真实生产流量、目标企业流程、付费模型全量压测、学习者试学和从业者签字评审。发布可以公开架构、资料页和已验证 fixture，但必须保留这些状态标签，不能宣传为生产验证完成。
