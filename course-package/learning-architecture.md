# 测试开发进入 AI 时代：完整学习架构

这份架构回答的不是“测试人员应该学哪个 AI 工具”，而是一个更专业的问题：一个已经掌握传统测试方法的工程师，怎样把原有能力迁移到 AI 产品、Agent 和持续评测体系中，并最终能用证据支持发布决策。

## Learner transformation

学习者的起点是会执行或编写测试；终点是能定义 AI 质量、拆解 AI 系统、构造评测数据、设计组合 Oracle、验证 Agent 轨迹、建立 CI 门禁、解释 Benchmark 分数，并把线上失败转成可重放的回归资产。

完整路径使用“双主线”：

- 职业主线：需求与风险 → 测试设计 → 数据与自动化 → 执行与诊断 → 发布 → 生产反馈。
- AI 主线：模型与推理 → LLM/RAG/Agent 结构 → 评测科学 → Agent/Workflow 质量 → 生产质量工程 → Benchmark。

两条主线不能分开教。每个 AI 概念必须落到一个测试决策、失败模式或学习者工件；每个传统测试模块必须说明在 AI 时代哪些原则保留、哪些对象和证据发生变化。

## Professional baseline

进入 AI 测试之前，学习者必须证明下面这些传统测试能力，而不是默认“做过几年测试就一定会”：

1. 能从需求、架构和代码变化识别业务风险，并形成追踪关系。
2. 会使用等价类、边界值、状态转换、组合、属性和风险切片设计测试。
3. 能定义 Oracle：哪些结果精确断言、哪些使用状态机、哪些需要人工判断。
4. 能构造测试数据、隔离依赖、管理 fixture，并区分测试代码问题与产品问题。
5. 能编写 API/UI/集成自动化，并让预埋缺陷稳定把测试从绿变红。
6. 能使用 Trace、Log、Screenshot、Network、Diff 建立缺陷证据链。
7. 理解测试分层、回归选择、Mutation、CI 门禁、Waiver 和发布责任。

阶段入口考核不是选择题：学习者提交一个小型可执行测试仓库，说明风险、数据、Oracle 和追踪关系；注入一个业务缺陷后必须稳定失败。未通过者先补传统测试桥接模块，不能直接跳到 LLM Judge。

## AI foundations

测试工程师不需要先成为模型训练研究员，但必须理解会改变测试结论的运行机制。

### 模型生命周期

数据收集与清洗 → 预训练 → 指令微调/对齐 → 离线评测 → 部署 → 推理 → 线上监控与反馈。测试人员需要知道训练数据与当前知识的关系、模型版本为什么影响行为、评测为什么可能被污染，以及线上反馈怎样进入下一轮数据或回归集。

### 推理时的最小知识

- Token：模型处理的是切分后的 token，不是人眼看到的完整词句；长度、语言和格式会影响上下文预算。
- Embedding：把内容映射为向量表示，常用于检索与相似度；“相似”不等于“业务正确”。
- Attention 与上下文：模型根据当前上下文建立关联；长上下文、位置、无关材料和冲突材料都会改变结果。
- Logits 与解码：模型产生下一个 token 的分布；temperature、top-p、随机种子和推理策略会影响重复性。
- Prompt 与结构化输出：提示词、系统指令、Schema、解析器和重试都是被测依赖。
- RAG：检索、排序、上下文拼接、生成和引用是不同层，必须分别留证据。
- Tool call 与 Agent：模型可能选择工具、参数和后续动作；最终文字正确不能抵消中间危险操作。
- State、Memory 与 Trace：多轮 Workflow 的状态、记忆、重试、handoff、预算和终止原因都属于测试对象。

基础阶段退出工件是一张“AI 系统结构与证据图”：标出输入、模型/Prompt/数据/工具版本、检索、工具调用、状态、最终输出、成本延迟和人工决策点。

## Capability transition matrix

| 传统能力 | 保留的原则 | AI 带来的变化 | 新能力与新工件 |
| --- | --- | --- | --- |
| 需求与风险分析 | 风险决定测试深度 | Prompt、模型、知识库和工具版本都可能改变业务行为 | AI 风险模型、版本影响矩阵、攻击面 |
| 测试设计与 Oracle | 结果必须可判定 | 输出是概率性、语义性且允许多种正确表达 | 组合 Oracle、Rubric、Judge 校准集、人工 Gate |
| 测试数据 | 数据决定覆盖 | Eval 数据还会污染、泄漏、漂移或被模型记住 | Dataset card、风险切片、Holdout、Lineage |
| 自动化测试 | 自动化必须能抓到缺陷 | AI 会生成或自愈测试，也可能删断言、放宽条件 | Mutation 报告、Semantic diff、自愈禁区 |
| 缺陷诊断 | 结论必须回到证据 | 错误可能来自检索、生成、工具、权限、状态或 Judge | 分层 Trace、失败分类、反事实诊断 |
| CI 与发布 | 门禁服务发布决策 | 质量具有统计波动，模型/Prompt/数据一起变化 | 版本清单、统计门禁、Waiver、回滚策略 |
| 生产监控 | 线上失败进入改进 | 需要采集 token、工具、检索、成本和用户反馈 | Trace-to-eval 流水线、漂移告警、隐私策略 |
| 行业 Benchmark | 测试必须可复现 | 榜单分数依赖数据、Prompt、Harness、Scorer 和权限 | Benchmark spec、复现实验、污染审计、Metric card |

## Learning stages

### 第一阶段：传统测试能力基线

先拆解研发测试流程、测试策略、测试设计、API/UI/集成自动化、数据、诊断、CI 和发布。交付传统测试基线仓库，完成一次产品缺陷注入。这里训练的是不会因 AI 出现而消失的专业判断。

### 第二阶段：大模型与 AI 系统运行基础

理解模型生命周期、Token、Embedding、Attention、上下文、解码、结构化输出、RAG、Tool call、Agent loop 和 Trace。交付 AI 系统结构与证据图，并能根据一个失败症状判断先检查哪一层。

### 第三阶段：AI 应用于传统测试

把 AI 放进需求分析、测试设计、自动化生成、测试数据、失败归因和维护流程。每个实验都要与非 AI 基线比较，并证明 AI 没有通过删除断言、放宽 Oracle 或制造伪证据获得“提效”。

### 第四阶段：测试 LLM、RAG 与多模态系统

学习评测任务、Eval case、黄金集、风险切片、Rubric、确定性 Scorer、LLM-as-judge 和人工校准；再分别测试 LLM 的正确性与拒答、RAG 的召回/忠实性/引用、多模态的 OCR/版面/视觉事实。阶段工件是一套能捕获已知回归的版本化 Eval 仓库。

### 第五阶段：测试 Agent 与 Workflow

区分固定 Workflow 与动态 Agent；测试最终结果、单步动作、完整轨迹、状态转换、循环、重试、handoff、工具参数、权限、预算、超时、终止条件和副作用。必须在沙箱中注入错工具、错参数、越权、循环和伪成功，并由独立 Verifier 拒绝。

### 第六阶段：AI Quality Engineering

把数据集、Prompt、模型、知识库、工具和 Scorer 一起版本化；把 Eval 接进 CI；保存 Trace；把脱敏线上失败变成回归样例；联合评估质量、延迟和成本；设计 Waiver、漂移告警、回滚和事故演练。

### 第七阶段：Benchmark 与分数工程

拆解公开与内部 Benchmark。学习任务如何构造、样本如何选取和标注、如何划分 Holdout、Prompt 和权限如何固定、Scorer 怎样产生每条样例分数、怎样聚合为 Accuracy/Pass@k/Resolved rate/Judge score、怎样计算不确定性、检查污染并版本化榜单。阶段工件是一份可复现的小型 Benchmark，而不是抄一张排行榜。

### 第八阶段：AI QE Capstone

交付一套职业相关的端到端质量仓库：Commit 触发评测，已知回归被阻断，Trace 支持诊断，线上失败可脱敏回流，Waiver 有审批和过期时间，Benchmark 版本变化可以解释。最终答辩必须说明哪些结论来自 fixture、哪些来自真实模型、哪些仍需从业者或生产验证。

## Specialization tracks

- LLM 质量：正确性、格式、拒答、稳定性、偏差、Judge 校准。
- RAG 质量：检索召回与污染、上下文、引用、忠实性、过期与冲突知识。
- Agent 质量：工具、参数、轨迹、权限、状态、循环、副作用和终态。
- Workflow 质量：固定编排、handoff、Worker、并发、重试、预算、可重放和业务不变量。
- Benchmark 工程：数据来源、任务协议、评分器、聚合、不确定性、污染、版本和维护。
- AI 辅助测试：PRD/Diff 风险、自动化生成、Fuzz、Trace 归因、自愈防作弊。

专业课程不要求所有人达到相同深度：自动化测试开发可以主修 AI 辅助测试和 Agent 测试；AI 应用质量工程师必须完成 LLM、RAG、Agent、Workflow 和 Benchmark；测试平台工程师还必须完成 CI、可观测性、漂移和治理。

## Benchmark literacy

课程讲“分数是怎么来的”，必须沿着同一条链路：

`任务定义 → 数据来源 → 样本选择 → 标注/参考答案 → Split/Holdout → Prompt 与运行权限 → 多次执行 → Scorer → 聚合 → 不确定性 → 污染审计 → 版本化报告`。

例如 SWE-bench 的 Resolved rate 不只是“模型写代码的能力”：它还依赖 Issue、仓库快照、环境、Agent scaffold、工具权限、超时和 FAIL_TO_PASS/PASS_TO_PASS 测试。AgentBench 的汇总分还依赖不同环境和奖励定义。HELM 强调按场景和多个指标透明报告，而不是压成一个万能总分。课程只教授可复现的历史或小型 fixture，不展示未经当前协议核验的模型排名。

## Exit gates

以下任一项成立，不能宣称完成专业学习路径：

- 未通过传统测试基线，只看完 AI 概念页；
- 不理解模型运行和系统结构，却直接使用评测工具；
- Eval 没有数据版本、风险切片、Oracle 或人工校准；
- RAG 只看总分，Agent 只看最终答案，Workflow 不检查状态和副作用；
- AI 生成或自愈测试没有 Mutation 证据；
- Benchmark 只有榜单数字，没有数据、协议、Scorer、聚合和污染说明；
- 生产门禁不能复现，Waiver 没有责任人和过期时间；
- 只有合成 fixture，却声称真实业务或生产有效。

当前交付边界：架构和第一条 RAG 评测路径已建立，传统测试桥接、大模型基础新增页面属于桌面研究内容；完整专题实验、真实模型运行、目标学员测评和企业生产验证仍需逐阶段建设。
