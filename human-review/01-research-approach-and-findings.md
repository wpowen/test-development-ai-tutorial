# 测试开发 × AI：调研思路与主要结论

调研快照日期：2026-08-10。本文只总结本轮已经打开、记录和分类的资料，不把搜索结果摘要当作证据。

## 调研链路

### 第一步：先理解测试开发的真实工作

我们没有从“有哪些 AI 工具”开始，而是先回答测试开发平时对什么结果负责。职业权威资料、专业能力体系和测试实践共同指向一条完整生命周期：

`理解需求与风险 → 设计质量策略 → 构建和执行检查 → 诊断失败 → 参与发布决策 → 用生产反馈持续改进`

沿着这条生命周期，再拆出三种角色：

- 自动化测试开发：面向 Web、API、移动端和传统业务系统；
- AI 应用质量工程师：面向 LLM、RAG、Agent 和多模态系统；
- 测试平台与质量基础设施工程师：面向 CI、评测数据、可观测性和发布门禁。

### 第二步：把职业拆成工作域，而不是工具章节

我们最终拆出 5 个工作域：

1. AI 输出与检索质量评测；
2. Agent 轨迹与安全验证；
3. AI 辅助测试设计与实现；
4. 失败诊断与证据链；
5. 发布门禁与生产反馈。

每个工作域继续追问：什么业务事件触发工作、输入输出是什么、失败会造成什么损失、AI 可以做什么、AI 不能替谁做决定。

### 第三步：七条检索路线并行搜索

| 检索路线 | 实际搜索的问题 | 用来证明什么 |
| --- | --- | --- |
| 职业权威 | 测试岗位的职责、工作产物、质量和风险边界 | 这个职业真实在做什么 |
| AI 一手资料 | LLM/RAG/Agent 评测、测试 Agent、红队、CI 能力 | 当前技术能否完成某种操作 |
| GitHub | 仓库、commit、Release、Issue、CI、License、运行入口 | 是否存在可审计实现 |
| 从业者与论坛 | 生成测试为何失效、自愈为何误修绿、浏览器 Agent 为何难验证 | 真实失败语言和反例 |
| 招聘 | eval、黄金集、轨迹、质量门禁、生产反馈等岗位要求 | 当前雇主是否提出相关任务 |
| 课程供给 | 海内外课程讲什么、交付什么、有没有可运行物料 | 市场已经怎么教育用户 |
| 反证 | Prompt injection、数据泄露、漂移、judge 不稳定、成本 | AI 在什么条件下不能直接使用 |

典型查询并不是一句“测试开发 AI”，而是多组组合：

- `software tester LLM evaluation golden dataset CI`；
- `RAG evaluation retrieval generation citation faithfulness`；
- `agent trajectory evaluation tool call parameter security`；
- `Playwright agent generated tests mutation can fail`；
- `AI quality engineer eval job golden dataset trajectory monitoring`；
- `大模型测试 课程 实战 RAG Agent 评测`；
- `LLM testing failure hallucination prompt injection excessive agency`。

### 第四步：来源不能互相冒充

同一家厂商的官网、博客和仓库不能算三个独立观点。每个来源都记录发布者和来源家族；高优先场景至少需要职业现实、AI 能力、实践/失败三类证据，而且来自至少三个独立来源家族。

GitHub 也不因为仓库存在就写成“实测可用”。本轮两个候选仓库只完成了版本和许可证审计，没有作为默认实验运行，因此仍标为 `metadata-only`。

### 第五步：把资料变成可教的业务场景

一条资料只有能走完下面链路才进入课程：

`角色 → 业务事件 → 输入 → 当前做法 → 失败代价 → AI 介入 → AI 新风险 → 可检查输出 → 人工决策 → 学员物料`

例如，“用 AI 测试 RAG”仍然太空泛。可教场景应该是：

> 客服知识库、Prompt 或模型版本准备发布时，测试开发使用版本化评测集分别检查检索、引用、拒答、工具调用、延迟和成本；注入一条错误退款承诺后，CI 必须变红，并由质量负责人决定阻断或批准例外。

这时才可以明确输入、输出、命令、指标、故障和责任边界。

### 第六步：先做覆盖矩阵和独立评审，再生成课程

本轮新增了一个前置门禁，避免以后继续依靠用户指出缺课。Skill 会把每个候选能力放进：

`职业工作域 × 学习层级 × AI 专题 × 学员水平 × 业务场景 × 学员工件 × 退出考核 × 证据状态`

然后从职业老兵、AI 系统工程师、评测质量专家、课程设计师、市场与学员研究、对抗审查六个视角独立找缺口。传统测试基线、大模型原理、Agent/Workflow 差异、Benchmark 分数工程和从业者验证不足，都是这一步主动发现的，不是按课程标题补出来的。

详细结果见 `../curriculum-gap-analysis.md`；机器可检查的覆盖关系见 `../research/curriculum-coverage-matrix.csv`。

## 主要结论

### 结论一：测试开发的 AI 机会不只是“生成测试用例”

真正新增的工作对象包括概率性输出、检索上下文、模型 judge、Agent 工具调用、轨迹、Prompt injection、漂移和生产反馈。这些问题移除 AI 后就不存在，因此 AI 是核心，不是装饰。

### 结论二：最有差异化的统一骨架是“可证伪”

公开课程经常强调模块很多、工具很多或效率提升，但对外页面较少同时展示：

- 可下载的离线输入；
- 明确的质量阈值；
- 故障注入；
- 机器可读失败报告；
- 修复后的回归证明；
- 可替换的工具适配层；
- 人工发布责任。

因此课程的稳定差异化不应是多教一个工具，而应是：每课都能证明检查真的会在有意义的回归上失败。

### 结论三：测试 AI 系统比普通“AI 辅助测试”更适合作为首个样课

“让 AI 从 PRD 生成测试用例”容易退化成通用 Prompt 教学，也很难判断生成结果是否真正理解业务。RAG/LLM 评测则可以明确数据集、指标、阈值、失败切片和发布门禁，更容易让学员看见职业价值。

### 结论四：小白第一课应该离线可复现，在线模型作为后续适配器

如果第一步就要求 API Key、企业知识库和付费模型，学员很容易卡在环境问题。本样课先用录制输出学习评测工程，再提供接入真实模型的升级路径。离线实验只能证明评测机制可运行，不能证明某个在线模型的真实质量。

### 结论五：课程最终要交付“质量资产”，不是知识点

测试开发学完后应该留下评测集、阈值、报告、故障样例、CI 门禁、检查清单和可复用 Skill。否则课程结束后，学员仍然不知道怎么迁移到自己的项目。

## Evidence

本轮较强证据包括：

- O*NET 的 Software Quality Assurance Analysts and Testers 职业任务，用于职业基线；
- Playwright Test Agents 官方文档，用于 planner、generator、healer 的能力事实；
- Promptfoo、DeepEval、Ragas、LangSmith、Inspect AI 官方资料，用于评测、RAG 指标、Agent 轨迹和 CI 能力；
- NIST AI RMF、OWASP LLM Top 10、ISTQB AI Testing Syllabus，用于风险、监控、安全和能力边界；
- 5 个独立雇主的原始招聘页，用于观察 eval、黄金集、轨迹、质量门禁和生产反馈等当前任务语言；
- 10 个直接课程或教程页面，用于观察市场供给和公开交付承诺；
- 40 个来源记录，其中新增 Attention、RAG、ReAct、HELM、lm-evaluation-harness、SWE-bench、AgentBench 和可信第三方评测方法，用于补齐运行机制和 Benchmark 链路。

这些证据支持“能力存在”“职业任务存在”“市场有相关供给和岗位语言”，但不直接支持“课程一定卖得好”或“学员一定提升绩效”。

## Inference

以下是基于多类证据形成的课程策略推断：

1. 测试开发 × AI 应建立四条课程主线，而不是围绕 ChatGPT、Claude、Playwright、LangChain 等品牌分章；
2. 每门课应固定使用业务输入、AI 工作流、故障注入、红绿验证和人工边界；
3. 课程视频用失败和结果开场，比先讲术语更适合小白；
4. 免费短视频负责让用户识别自己的职业问题，长课负责完整操作和物料交付；
5. 工具更新时替换 adapter 并重跑验收，职业问题和课程 ID 不随品牌变化。

这些结论是方法论选择，不是行业统计事实。

## Unknown

目前仍不知道：

- 中国测试开发群体对 20 个主题的真实搜索量、完课率和付费意愿；
- 真实企业是否愿意提供脱敏 RAG/Agent 项目用于课程验证；
- 不同经验水平的测试开发完成样课需要多长时间；
- 短视频开场是否能提升停留、收藏和资料领取；
- 课程中的教学阈值能否迁移到某个具体企业；
- 在线模型、检索器和 judge 在真实流量下的表现与成本。

下一阶段的市场验证不应该继续堆资料，而应拿细化样课做 5–10 位测试开发从业者盲评，再用短视频、资料领取和完成实验的数据验证需求。
